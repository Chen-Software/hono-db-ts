# Capacity: `Identifiable`

> The **identity** capacity. It gives every model instance a stable, type-tagged
> `id` and decides *where that id comes from*: supplied on the data, supplied as
> a trailing constructor arg, or auto-generated as a `uuid`. It is the
> **prerequisite** for the versioning, hashing, SQL-PK, and reference layers —
> anything that needs "which one is this?" starts here.

`Identifiable` is the smallest of the capacity set, and arguably the most
load-bearing: it owns the `id` field's *type* and *provenance*, and almost every
other capacity reads `id` downstream (`Versionable`/`Hashable` require it;
`SqlSerialisable` turns it into the primary key; `Referencible` points foreign
keys at it; `Servable` falls back to it for keyset pagination).

---

## 1. What it is / is not

| | |
|---|---|
| **Is** | a marker `IdentifiableSchema<TID>` declaring `readonly id`, plus a mixin that (a) supports a `(data, id)` constructor override and (b) auto-generates a `uuid` when no `id` is supplied. |
| **Is not** | a validator of the `uuid` *format* (that lives in the schema's `tags.Format<"uuid">`, enforced by `Validatable`/classify). A quota/sequence allocator. Anything to do with version timestamps (that's `Versionable`). |

It is **stateless and side-effect-free** at runtime: the only thing it does is
decide the `id` value at construction time. There is no registry, no counter, no
persistence — `crypto.randomUUID()` is the whole "mint" story.

---

## 2. The type marker

```ts
interface IdentifiableSchema<TID> {
  readonly id: TID | (string & tags.Format<"uuid">);
}
```

- The generic is **constrained**: `TID extends "uuid"`, so today `uuid` is the
  only id flavour. (`TID` is threaded through so a future `TID = "ulid"` or
  `"nanoid"` could be slotted in without widening the marker.)
- `readonly` — once set, the id never changes. This is the single most important
  invariant the capacity enforces: **`id` is permanent; the only thing that
  "rotates" on an update is `Versionable`'s `updated_at`.** `Versionable` leans
  on exactly this (`versionableUpdate` strips `id` from the patch and re-stamps
  `updated_at` instead).

Models declare the marker on their *data* interface, independently of whether the
mixin is applied:

```ts
interface PostSchema extends IdentifiableSchema<UUID>, TimestampedSchema, Versionable { … }
```

`UUID` is a project type alias (`string & tags.Format<"uuid">`).

---

## 3. What the mixin adds

```ts
function Identifiable<TID extends "uuid", TBase extends CapacityComposer>(Base: TBase) {
  Base.prototype.capacities && Base.prototype.addCapacity("Identifiable");
  return class extends Base implements IdentifiableSchema<TID> {
    declare readonly id: TID;
    constructor(...args: any[]) {
      if (args.length >= 2) {            // legacy (data, id) override form
        const id = args.pop();
        super(...args);
        this.id = id;
      } else {                           // canonical new X(data) form
        super(...args);
        if ((this as any).id == null) (this as any).id = crypto.randomUUID();
      }
    }
  };
}
```

Two construction paths, both routed through the base class's `new X(data)` form:

1. **`new X(data)`** — the model's canonical `from(data)` path, where `id` lives
   *on the data*. If `data.id` is present it is kept; if `null`/`undefined`, a
   fresh `uuid` is minted.
2. **`new X(data, id)`** — a legacy override form. The trailing `id` arg is
   **popped** and assigned after `super()`, overriding whatever the data carried.
   The pop only happens when a second arg is *actually* present — otherwise we'd
   strip `data` off `args` and hand the base an empty constructor (which fails
   classification). This dual handling mirrors `Timestamped`'s constructor.

### The `declare readonly id` detail

Under `useDefineForClassFields`, a plain `readonly id: TID;` field declaration
with **no initialiser** would RESET `id` to `undefined` after `super()` returns
(the base constructor assigns it from the data, then the field definition runs
and clobbers it). `declare` erases the runtime initialiser so the value the base
constructor set survives. (`Timestamped` uses the identical trick for
`created_at`.)

### UUID generation rule

- **Supplied `id` wins** — no re-generation, no re-formatting. The mixin trusts
  whatever the data/override carries.
- **Missing `id` → `crypto.randomUUID()`** — RFC-4122 v4, generated by the host
  (`crypto` global). This runs at *construction*, so `Post.random()` (via
  `Randomisable`) and `Post.from({…without id})` both get a real uuid.

> **Format enforcement is NOT here.** The mixin does not check that `id` is a
> valid uuid shape. That check lives in the schema's `tags.Format<"uuid">` and is
> enforced by `Validatable`/classify — proven by `post.test.ts`:
> `Post.is({ ...valid, id: "not-a-uuid" })` returns `false`. So `Identifiable`
> owns id *presence + provenance*; the *format* is a schema/`Validatable`
> concern. (Contrast `Hashable`'s `Sha256` tag, which is syntactic-only and must
> be checked via `verify()` — `uuid` is a *recognised* typia format and *is*
> validated.)

## 4. Composition

`Identifiable` takes **no options** — its signature is `(Base, mod)` with no
third options object (like `Immutable`, unlike `Queriable`/`Servable`/`SqlSerialisable`).

It is **Triggerable-gated**: registration is `Base.prototype.capacities &&
Base.prototype.addCapacity("Identifiable")`, so it only enters the capacity set
when `Triggerable` was applied first (innermost). The ordering caveat from
`triggerable.test.ts` applies verbatim: a capacity applied *before* `Triggerable`
is silently dropped.

Applied in the `capacities` array of every persisted model:

```ts
const PostModel = defineModel<PostSchema>({
  schemaName: "PostSchema",
  schemaModule: PostSchemaModule,
  capacities: [
    Identifiable,          // ← here
    Timestamped,
    JsonSerialisable,
    ProtobufEncodable,
    { capacity: SqlSerialisable, options: { name: "posts", dialect: "sqlite" } },
    { capacity: Queriable, options: { fields: { authorId: { as: "author" } } } },
    { capacity: Servable, options: { sort: { field: "updated_at", dir: "desc" } } },
    Immutable,             // LAST
  ],
});
class Post extends PostModel {}   // the model class does NOT re-apply the mixin
```

> The comment you'll see in `user.ts` ("We intentionally do NOT apply the
> `Identifiable` mixin here") refers to the **`User` subclass** (`class User
> extends UserModel {}`) — the mixin is already applied once inside
> `defineModel`'s `capacities` array. It is *not* saying the model skips
> `Identifiable`; `User`, `Post`, `Board`, `Thread`, and `Reply` all compose it.

### Use-or-ignore split (the capacity idiom)

Like every capacity, `Identifiable`'s *runtime* behaviour is bound concretely at
the model's own site (the constructor closure reads `this.id` and calls
`crypto.randomUUID()`), not generic inside `defineModel`. The mixin is "use it or
ignore it" — a model can omit it, in which case it owns its `id` story itself.
But in this codebase **every model composes it**, because the SQL/version/reference
layers all assume a `uuid` `id`.

## 5. API surface

`Identifiable` is almost entirely a **constructor concern** — it adds no statics
and no instance methods of its own (unlike `Versionable` which lifts a toolkit,
or `Servable` which lifts `serve`). Its entire surface is the `id` field plus the
construction behaviour in §3.

| Member | Kind | Source | Notes |
|---|---|---|---|
| `id` | instance field | marker + constructor | `readonly`, `uuid`. Set from data, from the `(data, id)` override, or minted. |
| `new X(data)` | constructor | mixin | canonical `from` path; mints uuid if `data.id` null. |
| `new X(data, id)` | constructor | mixin | legacy override; trailing `id` wins. |

That's it. The *interesting* behaviour is downstream — see §7.

---

## 6. The `id` is the anchor for everything else

This is the section that matters for the rest of the capacity set.

- **`SqlSerialisable` → primary key.** `deriveSqlPlan` flags `name === "id"` as
  `isId: true`, and `toDrizzleTable` calls `col.primaryKey()` for it. Every model
  table's PK is exactly `Identifiable`'s `id`. (`sql-serialisable.md` §3/§4.)
- **[`Referencible`](./capacity-referencible.md) / foreign keys target `id`.** `Reference<…>` resolves to the
  target model's `id` column by default (`column ?? "id"`). `Post.authorId` is a
  `Reference` to `User.id`. So `Identifiable` is what makes the relational graph
  possible.
- **`Versionable` requires it.** Every `Versionable` helper is generic over
  `Identifiable<string> & Versionable` — `nextUpdatedAt`, `withVersionBump`,
  `versionableUpdate`, `createVersionableUpdate`, `latestOf`, `isNewerThan`,
  `compareVersions` all take `T extends Identifiable<string> & Versionable`. The
  reason: version history is *keyed by `id`* (the append-only log is "all versions
  with this id"). `Versionable` owns the timestamp; `Identifiable` owns the key.
- **`Hashable` requires it.** `Hashable.updateHash` and `updateFor`/`updateForVersionable`
  are generic over `Identifiable<string> & …` — content addressing needs a stable
  subject id. (`hashable.md` §3.)
- **`Queriable` / `Servable` → `id` is a query field + cursor fallback.** Because
  `id` is a `uuid`/`string`, the matcher infers **substring** mode — so
  `?id=<prefix>` works (useful for partial-key lookups). And `Servable`'s keyset
  pagination falls back to the primary key (`id`) as the sort key when the model
  declares no `created_at`/`updated_at`. (`queriable.md` §3, `servable.md` §4.)
- **`JSON` / `Protobuf` carry it.** `toJSON`/`fromJSON` and `encode`/`decode`
  serialise `id` as an ordinary field (a 36-char uuid string / 32-hex for the
  wire formats). (`json-serialisable.md`, `protobuf-encodable.md`.)
- **[`Randomisable`](./capacity-randomisable.md) produces one.** `Model.random()` pipes typia's `createRandom`
  payload through `new this(...)`, which routes through `Identifiable`'s
  constructor — so a random user gets a real `uuid` (unless the schema's
  `random` generator overrides it). ([`randomisable`](./capacity-randomisable.md) capacity.)
- **`Triggerable` gates registration.** As noted in §4.

## 7. Sibling capacities

| Capacity | Relationship to `Identifiable` |
|---|---|
| `Versionable` | **requires** it — version history is keyed by `id`; all helpers are `Identifiable & Versionable`. |
| `Hashable` | **requires** it — content addressing needs a stable subject `id`. |
| `SqlSerialisable` | `id` → `primaryKey()`; the column the FKs reference. |
| [`Referencible`](./capacity-referencible.md) | FK targets default to `id`; `Identifiable` is what makes relations resolvable. |
| `Queriable` / `Servable` | `id` is a substring-matchable query field; `Servable` cursor falls back to `id` as sort key. |
| `JsonSerialisable` / `ProtobufEncodable` | carry `id` as a serialised field (uuid string / hex). |
| [`Randomisable`](./capacity-randomisable.md) | `random()` routes through the `Identifiable` constructor → real uuid. |
| `Timestamped` | orthogonal — `created_at` is minted the same dual-arg way; they compose as a pair. |
| `Immutable` | orthogonal — `id` is already `readonly`; `Immutable` freezes the whole instance including `id`. |
| `Triggerable` | registration gate — `Identifiable` only registers when `Triggerable` is innermost. |
| `Validatable` | enforces the `uuid` *format* of `id` during classify (the part `Identifiable` itself skips). |

## 8. Gotchas

1. **`declare` or lose your id.** Under `useDefineForClassFields`, writing
   `readonly id: TID;` without `declare` resets `id` to `undefined` after
   `super()`. The capacity uses `declare` for exactly this reason.
2. **The `(data, id)` form pops, it doesn't merge.** A second arg is treated as
   *the* id and removed from `args` before `super()`. Don't pass `(data, id,
   extra)` expecting `extra` to survive.
3. **Auto-uuid only fires on `null`/`undefined`.** A *falsy-but-present* `id`
   (e.g. `""`) is kept as-is; only a missing id is minted. Set a real uuid or
   leave it off entirely.
4. **Format validity is `Validatable`'s job, not this capacity's.** A malformed
   uuid passes `Identifiable` construction but fails `Validatable.assert`/classify
   (so `Post.is({…id:"not-a-uuid"})` is `false`).
5. **`id` is permanent.** Nothing in the codebase re-assigns `id`. `Versionable`
   updates rotate `updated_at`, never `id` — by design, so the version log stays
   coherent.
6. **Triggerable ordering.** Apply `Triggerable` first (innermost); a capacity
   composed before it is silently dropped from the registry.
